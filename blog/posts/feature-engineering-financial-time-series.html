Return Distribution — Raw vs. Normalised

Why Normalise?

Raw financial returns are fat-tailed and often skewed. Many ML models assume roughly Gaussian inputs. Log or z-score normalisation compresses extreme values and makes the distribution more symmetric, improving gradient stability and model convergence.

Key Concepts

Lag Feature

A copy of a variable shifted backwards in time. lag_1 = yesterday's close. Injects historical context without leaking future information.

Rolling Window

Aggregate calculations (mean, std, min, max) over a fixed-size window that slides along the time axis. Window size controls how much history is captured.

Stationarity

A time series is stationary when its mean and variance are stable over time. Raw prices are non-stationary; returns and differences usually are. Required by many ML models.

Feature Leakage

When future information bleeds into features used for training. A common trap with rolling features if the window is computed with look-ahead data. Always use .shift(1) after rolling.

RSI (Relative Strength Index)

A momentum oscillator (0–100) measuring the speed and magnitude of recent price changes. Values above 70 suggest overbought conditions; below 30, oversold.

Bollinger Bands

A volatility indicator: a moving average with ±2 standard deviation bands. The bandwidth (%B) is a useful normalised feature for ML models.

Feature Engineering for Financial Time-Series

Raw OHLCV data tells you what happened. Features tell a model how to think about it. Here's the practical process I use for turning price data into a matrix that a gradient boosted tree or neural network can actually learn from.

Python Machine Learning Feature Engineering Finance

If you've worked with financial data for any length of time, you'll know that feeding raw OHLCV prices directly into a model is almost always a bad idea. Prices are non-stationary, the signal-to-noise ratio is brutal, and most models have no way to reason about the sequence of values without some help from you. Feature engineering is where that help comes from.

This post walks through the pipeline I use — from cleaning raw data through to a feature matrix ready for training. The Visuals panel on the right has an interactive pipeline diagram, distribution charts, and a concept glossary.

Code context

All examples use pandas and ta-lib (or the ta package). The patterns transfer directly to any framework. Dataset: daily OHLCV for a single equity, ~5 years.

1. Start with clean, stationary data

Before a single feature is created, the data needs to be in a reliable state. For daily equity data that means:

  • Adjust for corporate actions. Splits and dividends create artificial jumps. Always work with adjusted close prices.
  • Handle missing sessions. Forward-fill gaps from market holidays so rolling calculations don't skip.
  • Convert prices to returns. Log returns (np.log(close / close.shift(1))) are approximately stationary and well-behaved for most models. Raw prices are neither.
import pandas as pd
import numpy as np

df = pd.read_csv("ohlcv.csv", parse_dates=["date"], index_col="date")
df = df.sort_index().asfreq("B").ffill()  # business-day frequency, forward-fill

df["log_return"] = np.log(df["close"] / df["close"].shift(1))

2. Lag features — giving the model a memory

A lag feature is simply a variable shifted backwards in time. lag_1 is yesterday's value, lag_5 is five trading days ago. They're the simplest way to tell a non-sequence model "here's what happened recently". 

for lag in [1, 2, 3, 5, 10, 21]:
    df[f"ret_lag_{lag}"] = df["log_return"].shift(lag)

# Volume lags are also valuable — volume precedes price moves
for lag in [1, 2, 5]:
    df[f"vol_lag_{lag}"] = df["volume"].shift(lag)

The .shift(lag) is critical. Without it, you'd be using today's return to predict today's return — that's target leakage, and your validation score will look spectacular right up until you trade it live.

3. Rolling statistics — capturing regime context

Where lag features capture specific past moments, rolling statistics summarise the character of recent history: how volatile has it been? Is price trending? Is volume elevated? I typically compute these over multiple windows to capture both short-term and medium-term regimes. 

for window in [5, 10, 20, 60]:
    roll = df["log_return"].rolling(window)
    df[f"ret_mean_{window}"] = roll.mean().shift(1)   # shift to avoid leakage
    df[f"ret_std_{window}"]  = roll.std().shift(1)
    df[f"ret_skew_{window}"] = roll.skew().shift(1)

    # Price relative to rolling mean (mean-reversion signal)
    sma = df["close"].rolling(window).mean().shift(1)
    df[f"close_vs_sma_{window}"] = (df["close"] - sma) / sma

The ret_std_20 column — 20-day rolling volatility — is one of the most consistently informative features in my experience. High-volatility regimes behave very differently from low-volatility ones, and models that can't distinguish them tend to perform poorly at exactly the wrong times.

4. Technical indicators — encoding domain knowledge

Technical indicators are essentially pre-built rolling calculations with financial domain semantics baked in. RSI, MACD, and Bollinger Bands are the three I find most reliably useful as ML features — not because they predict price direction directly, but because they encode regime information in a compact, normalised form. 

import ta

# RSI (14-day)
df["rsi_14"] = ta.momentum.RSIIndicator(df["close"], window=14).rsi()

# MACD signal line and histogram
macd = ta.trend.MACD(df["close"])
df["macd_diff"] = macd.macd_diff()   # histogram: fast signal minus slow signal

# Bollinger Band %B (where is price within the bands?)
bb = ta.volatility.BollingerBands(df["close"], window=20, window_dev=2)
df["bb_pct"] = bb.bollinger_pband()   # 0 = lower band, 1 = upper band

# Shift all indicators by 1 to prevent leakage
indicator_cols = ["rsi_14", "macd_diff", "bb_pct"]
df[indicator_cols] = df[indicator_cols].shift(1)
One gotcha: many ta library functions compute indicators using the current bar's close. Always .shift(1) them before using as model inputs.

5. Normalisation and the final feature matrix

Most gradient-boosted tree models are scale-invariant, but neural networks and linear models aren't. I apply z-score normalisation using a rolling window to avoid look-ahead bias — the mean and standard deviation are estimated only from the past, not the full dataset. 

feature_cols = [c for c in df.columns if c not in ["open","high","low","close","volume"]]

# Rolling z-score normalisation (252-day window ≈ 1 trading year)
for col in feature_cols:
    roll = df[col].rolling(252, min_periods=60)
    df[col] = (df[col] - roll.mean().shift(1)) / (roll.std().shift(1) + 1e-8)

# Drop rows with NaN (warm-up period for rolling windows)
df = df.dropna()

After this step you have a feature matrix where every column is a rolling z-score, approximately mean-zero with unit variance, computed purely from past data. Feed it to your model of choice.

Putting it all together

The full pipeline is roughly 60 lines of pandas. The discipline it enforces is simple but worth repeating: every feature must be computed using only information available at prediction time. .shift(1) after every rolling operation. Test on a held-out time window, never a random split.
